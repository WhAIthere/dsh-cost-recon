### 1d. 修的 bug：「显示具体 token 数」打不开（2026-09-28）

## 3. 数据源与凭据（改这块前先读）

- **官方小时桶**：`GET platform.deepseek.com/api/v0/usage/by_api_key/amount|cost?start=&end=&tz=`，
  `Authorization: Bearer <userToken>`，**单日窗口才返回 `bucket=3600`**；多日是 86400。
- **token 存哪**：`token统计/usertoken.txt`（取自平台 `localStorage['userToken']`，
  浏览器里 `copy(JSON.parse(localStorage.getItem('userToken')).value)`）。
  **规矩：只本机读、绝不写进任何产物、绝不外传；`dashboard.html` 里绝不内联 token。**
- **只认一把 key**：`db.KEY_NAME = "harness"`（平台 id `1bcbb7ee…`）。
  同账户还有一把 `codex`（`42c83dae…`）**完全不参与**统计——它正是"账本 ≠ 官方(harness)"的原因。
- **限流**：实测吃过 429。一天 2 个请求、每次间隔 ≥1.5s（默认）、429/5xx 指数退避、
  **只补缺的天**（最近 1 天默认重抓，因为当天数据还在长）。
- 本机 TLS 证书验证过不去（Steam++ 劫持）→ `ds_usage.py` 自动降级为不验证证书（本机专用）。

## 4. 口径与规则（别改坏）

1. **聚合必须 `AND keep=1`**（铁律）。中断空壳恒 `keep=0`，所以天然不进任何统计。
2. **恢复 = 对账，不是平账**：只认同**一个小时**的官方差额（官方小时 − 我们 keep=1）；
   差额 ≤ 0 或该小时没有唯一中断 → **留空**；多笔时按中断时**正文长度加权**，否则**均分**（写进 `est_note`）。
   **禁止**按天分摊、**禁止**拿账号级余额差当池子（历史事故：把同账户别的 API 在别的时段花的钱
   摊到晚上的中断上）。
3. **fork 副本**：同一次中断在兄弟会话里有多份（`msg_id` 相同）→ 只算最早的 `replayed=0`，
   副本 `replayed=1` 不参与分配、不重复计钱。
4. **对不上的差额只报出来**（KPI / 对账表 / `official_recon.log`），不塞给任何行。
5. **精度**：账本列上限是"分"（官方 `/user/balance` 只给两位小数）；全精度列（官方/events/ledger/折算）3 位；
   系数 = **官方÷折算**，不要用账本÷折算。
6. **改完必跑自测**；**改了去重/归属 → `--full --recon` 重扫一次**；
   新增"影响哪些行进树/行里数字"的开关**必须写进 `app.js` 的 `treeKey()`**。
7. **高峰倍率以校验为准**（2026-09-28 加）：每次扫描末尾 `db.apply_official_peak()` 会用官方小时桶
   实测的倍率校正 `messages.peak / cost_est`（判定是"拿官方 token 分别按**谷价/峰价**各折一次，
   谁更接近官方金额就用谁"）；**没有官方数据的小时保持原判定**。
   **节假日表（`config/holidays.txt`）只作对照、不参与算钱**；调休按普通周末（DS 不认调休）。
   它必须在 `rebuild_session_aggs()` **之前**跑，否则 sessions 的 `peak_cost/offpeak_cost` 会脱节。
8. **价目按 (模型, 时刻) 查表**（`config/prices.txt`，v5 加）：命中档号写进 `messages.price_row`；
   **匹配不到 / 多档重叠 = 未知价目 → `price_row=-1`、`cost_est=-1`，钱不计、token 照算**。
   所以**每一处金额聚合都要带 `AND cost_est >= 0`**（`keep=1` 的孪生铁律）；
   生效区间按北京时间、起含止不含；峰价不一定是谷价的 2 倍，**别写死 ×2**。

## 6. 下一步更改思路（按建议优先级）

### ① 节假日"不走高峰"规则（✅ 2026-09-28 已做完，采用方案 B 的变体）
- 现象：2026-09-25（中秋节）官方把 14/15/16 点按**半价**收（比值精确 0.500），我们按高峰 ×2。
- **实际做法**：不以节假日表算钱，而是**用官方小时数据自校准**（倍数 = 官方金额 ÷ 官方 token
  刊例价，≈2 峰 / ≈1 谷），落 `official_peak` 表并直接校正 `messages.peak / cost_est`；
  节假日表 `config/holidays.txt` 只作对照（`src/holiday_check.py`），**不参与开销计算**。
  详见 MAINTAIN.md §2.7。
- 验收（09-25 残差 0.986 → 0.015）**已达成**；剩下的是**等 10-10（周六调休上班）复核"
  DS 不认调休"这条**：那天跑一次 `holiday_check` 看库内标记对不对。
- 覆盖面：只有**抓过官方小时桶的那些天**才享受校准（目前 09-17 ~ 09-28）；更早/更晚的天
  仍是"周末 + 窗口"的规则判定。要扩大就多抓几天官方数据（`ds_usage.py --days N`）。

### ② 09-17 / 09-18 的缺口（无中断却差 6~7%）
- 已知线索：官方 requests 数 vs 我们的调用数；`day_model.calls`（DSH 原生）也在库里可对比。
- 建议做法：把差**按小时**摊开看集中在哪些小时 → 若是旁路（title/search）未归钱，量级能否对上；
  再看那两天有没有"被漏扫的会话"（多版本目录、崩溃补票）。
- 验收：给出结论（是旁路、漏扫、还是官方侧含我们看不到的请求），并决定是否需要补记。

### ③ 09-24 残差 0.431
- 官方 requests 1013 vs 我们 1005 → 差 8 次。查是否有**第 7 次中断没有落盘**（那就永远补不上，
  只能留在"对不上"里），或那 8 次分布在哪些小时。

- 「中断恢复」独立小视图：哪天几次中断、恢复多少、哪次没恢复。
