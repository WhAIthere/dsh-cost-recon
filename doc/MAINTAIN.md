## 0. 一分钟速览

- **这是什么**：把 DSH 的 token 用量与花费，做成分层可下钻的本地看板。
- **入口**：`刷新看板.bat`（刷新数据+打开看板）／`dashboard.html`（看板本体）／`看板.html`（中文名跳转页）
- **数据源**：`~/.dsh/.dshw-usage.json`（账本，钱最准）、`~/.dsh/dsh-usage/usage-ledger.json`（按天×模型明细）、
  `~/.dsh/sessions/*/*/session.vN.jsonl.zstd`（逐次调用，能下钻）、
  `~/.dsh/search-usage.jsonl`（**原生搜索旁路账单**，见 §2.10）、
  `~/.dsh/storages/{workspace.json, session_projcache/}`（显示名）
- **本地库**：`temp/token_stats.db`（SQLite，可随时删了重扫）
- **只读原则**：本工具**从不写回** DSH 的任何文件，只读源 + 写自己的 `temp/` 与产物
- **跑之前先关 DSH**：否则最后几分钟的会话日志还在写盘，拿到的数据不完整

## 2. 数据模型（口径是这套东西的命根子）

### 2.1 三张核心表

| 表 | 粒度 | 说明 |
|---|---|---|
| `messages` | **一次模型调用**（一条 `assistant/message` 的 usage） | 最细单元，所有统计的源头 |
| `sessions` | 一个会话 | 从 `messages` 聚合而来（**必须带 `keep=1`**） |
| `labels` | 显示名 | **纯展示，绝不参与统计** |

其余：`day_model`（账本明细）、`events`（逐次实付）、`snapshots`（余额快照）、
`day_recon`（对账）、`side_calls`（旁路）、`sync_log`（增量）、`meta`。

### 2.2 必须记住的四条口径

1. **一个会话目录只读版本号最大的日志**（`session.v3` vs `v4`）。实测 v4 恒 ⊇ v3。
2. **fork/resume 会重放历史**：同一批调用以新 `message.id` 复制进新会话文件。
   去重键 = `(msg_id, in, out, cache_read, cache_write)`，**全局按时间排序后归最早那次**，
   其余标 `keep=0`——**存着可查，但不计钱不计 token**。
   不去重的后果实测过：09-23 那天会从 7.99 元算成 44 元。
   ⚠️ **2026-10-19 补的规则：同一时刻（ts 相同）的副本要比"会话创建时间"**。
   分叉副本的 ts 和原件一模一样，只比 ts（严格小于）分不出胜负；原创会话一被重扫，
   它的旧行刚被删掉、库里只剩副本 → 原件也被判成"重放"，**两边都 keep=0、整轮凭空消失**
   （实测今天丢了 8 轮 / 4.37 元）。现在归属键是 `(ts, 会话 created_at, session_id)`：
   同一时刻先认创建更早的会话（= 原创那一边），结果稳定、可重放。
   自测 `tie.*` 一组守这条。
   ⚠️ **2026-10-20 又补一层：裁决必须"全局唯一"**。以前只给"本次扫到的行"下结论，
   后来居上的那份会把自己判成 keep=1，而**原来那个赢家（在别的会话里、没被重扫）还挂着 keep=1**
   → 同一调用被算两遍（实测 09-23 有 5 份都在算、那天算成 249%）。现在谁上位就降级上一个赢家：
   库里已有的行直接 `UPDATE ... keep=0, replayed=1`；本轮另一份待插入的行就翻它的 `new_keep`。
   自测 `tie.repair_*` / `tie2.*` 守这条（"后来居上"的顺序也覆盖了）。
3. **所有聚合必须带 `AND keep=1`**。踩过坑：`sessions` 聚合漏了过滤，导致
   "会话维度"比"消息维度"多算。
4. **钱有两个口径**：`cost_est` 是按刊例价折算（用于归因），余额账本是实付（用于对账）。
   逐日差额记在 `day_recon.factor`，实测 0.975~1.17。**token 是实测值，不需要校准。**
5. **价目按 (模型, 时刻) 查表**（`config/prices.txt` → `prices.py`），命中的档号记进 `messages.price_row`；
   **匹配不到 = 未知价目：`price_row = -1`、`cost_est = -1`，钱一律不计**（界面显示横杠 + 蓝问号）。
   ⚠️ 因此**每一处金额聚合都必须带 `AND cost_est >= 0`** —— 这是 `AND keep=1` 的孪生铁律。
   `-1` 是**响亮**的哨兵：漏了过滤会当场把总数算错（而不是悄悄少算几个钱），所以容易被抓出来。

### 2.3 显示名（纯展示层）

| 显示什么 | 来源 | 例子 |
|---|---|---|
| 工作区名 | `~/.dsh/storages/workspace.json` → `tables.workspaces[*].title` | `2-兴趣代码` |
| 会话名 | `~/.dsh/storages/session_projcache/sessions/<id>.json` → `record.rows.title.val` | `分析工作区D题目Q4` |
| 轮次摘要 | 同文件 → `record.rows.turnOutline.val.turns[*].prompt`（用户提问，截 14 字） | `第33轮 刚才出问题了…` |

**铁律：显示名缺了就回落显示 id，永远不能影响数字。**
自测里有专门的用例：清空标签后，所有行的数字必须逐字不变。

### 2.4 派生显示名：机器标题的子代理会话（2026-09-25 加）

Mnemon / DSH 会 spawn 各种**一次性子代理**，标题是 DSH 从注入指令生成的英文句子
（`Execute this remember request now`、`Bounded completed checkpoint (untrusted …`、
`Side: New thread`…），几十上百个会话重名、在树里既认不出谁是谁、看着也难受。

做法：每个子代理日志里都有一条**结构化的** `subagent/descriptor.label`（枚举值，比标题可靠），
用一张映射表把它翻译成中文名。**目录在 `src/subagent_names.py` 的 `RULES`**：

```python
# (label, prefix, 会话名模板, 轮次名模板)    占位符：{space}{name}{insight}{batch}{event}{doc}{head}
("Mnemon remember",              False, "记忆写入 → {space}", "记忆写入：{head}"),
("Mnemon idle checkpoint review", False, "空闲自检",          "空闲自检：事件 {event}"),
("Route runtime memory archive batch", True, "记忆归档 第{batch}批", "记忆归档 第{batch}批"),
...
```

| 读什么 | 从哪来 | 变成 |
|---|---|---|
| 写进哪个空间 | `mnemon_remember` 回执的 `memoryBodyName` → 日志里"空间目录"的 id→name(`"id": X, "name": Y`) → 请求体 `Preferred Memory Space ID` | `记忆写入 → 兴趣代码` / `记忆删除 → 长期记忆` |
| 叫什么名字 | 注入请求体里的行首 `- Name:` | `新建记忆空间：数阵` / `更新记忆空间：月露&墨雨猫` |
| 干什么的 | `- Insight ID:` / `checkpoint event N` / `Document title:` / 内容首行 | `记忆删除：8bc81283` / `空闲自检：事件 228` / `文档归档：…` |

**加新条目**：`python src\subagent_names.py --list` 看目录，
`python src\subagent_names.py --unmapped` 扫真实库、列出没收录的 label（带次数/花费/样例标题），
加一行 `RULES`，跑 `python src\tests\run_tests.py`（有 `derived.*` 一组建模用例兜底）。
2026-09-25 实测：213 个已收录、5 种未收录（`Extract vocab papers …`、`Gather domestic LLM API pricing` 等，
**它们标题本来就是中文**，所以不需要收录）。

落库与三条守卫（都在 `scan_sessions.sync_derived_labels()`）：

1. 派生名写进 `labels`，`src='derived'`（轮次行同），**纯显示、一个字都不进统计**；
2. `sync_labels` 的 upsert 带 `WHERE labels.src <> 'derived'` —— 否则下次扫描 projcache 的英文标题
   就把派生名冲回去了（projcache 每次都全量重写 labels）；
3. **候选＝标题是纯 ASCII、且 src 仍是 projcache 的会话**（中文标题的人看着不难受，不动它）。
   译不出来的 label **不改名**，但写一条 `kind='derived_none'` 标记（`load_labels` 会忽略这个 kind），
   免得每次扫描把同一个文件重读一遍 —— 增量友好：首次读 213 个文件约几 MB，之后为 0。

已知代价：`projcache` 里没有标题的会话不会被改名（它同时也不会在树里显示名字）。
空间 id `default` 是**按工作区分身**的（本区叫「兴趣代码」，别的区可能叫「每日」「长期记忆」），
所以空间名必须从日志回执里取，不能拿 id 反查本区的空间表。


### 2.5 起止时间

- 轮次：**用户提问时间 → 该轮最后一次 API 回复时间**
- 会话 / 工作区 / 天：其下所有轮次的 **最小起点 → 最大终点**
- 时间排序按**结束时间**（最后一次活动）比，不是起点（否则"很早就开始、刚刚还在用"的会沉底）
- `user/message` 记录**没有 turn 号**，只能按日志顺序配：遇到某轮 assistant 之前最近的
  一条 user/message 即该轮起点（超过 6 小时则不认，回落到 assistant 自己的时间）

### 2.6 中断空壳（异常）与恢复（2026-09-28 加，库结构 v4）

**现象**：DSH 循环思考/罢工、被你中断的那一步，日志里**有记录但没有 usage**——
`assistant/message` 记录在、`data.interrupted = true` 标记在、毫秒 `time` 在、中断前的正文在，
**只有 token 那五项没有**。所以它是"有记录、没钱"。

**采集**（`scan_sessions.parse_session`）：这类记录也入库，但
- token 全 0、`cost_est` = 0；`chars` = 中断时正文长度（分配时加权用）
- **强制 `keep = 0`** → 天然不进任何聚合（铁律 `AND keep=1` 一点没动），却能显示、能统计
- 列：`interrupted=1`、`est_cost` / `est_tokens`（恢复出来的值）、`est_note`（怎么分的）
- **fork 副本照旧去重**：同一次中断在兄弟会话里有好几份（`msg_id` 相同），只有最早那份
  `replayed=0`，其余标 `replayed=1`（次数才不会虚高、钱也不会重复分）

**口径安全的关键**：库结构升级时 `db._migrate()` 给老库补列，`scan()` 发现
`meta.schema_version` 变了就**自动全量重扫一次**（增量只重扫变动过的会话，新列填不上）。
⚠️ **改了去重/归属逻辑也必须 `--full` 重扫一次**，否则老行还是旧结果（踩过）。

**观察层 = 官方小时桶**（`src/ds_usage.py` → `official_hour` 表）：

- 端点 `platform.deepseek.com/api/v0/usage/by_api_key/amount|cost`，`Authorization: Bearer <userToken>`
  （token 取自平台 `localStorage['userToken']`，放在 `config/usertoken.txt`（工具目录下））
- **单日窗口才返回 `bucket=3600`**（小时桶），所以一天两个请求；**只认一把 key**（`db.KEY_NAME = "harness"`），
  同账户下别的 key（codex）概不参与
- 限流很紧（实测吃过 429）：每次请求之间 sleep（默认 1.5s，命令行可调），429/5xx 指数退避，
  **只补缺的天**（最近 1 天默认重抓，当天数据还在长）
- token 只在本机读，**绝不写进任何产物、绝不外传**

**恢复 / 对账**（`db.sync_gap_estimates` + `db.gap_summary`，每次清零后重写）：

**原则：这是"对账"，不是"平账"** —— 能对应上的就对应，对不上的**直接空着**。
（2026-09-28 走过一次弯路：拿"当天账本 − 我们"当池子按天分摊，池子必然分完 → 总额强行等于官方，
还把同账户下**别的 API 在别的时段**花的钱摊到晚上空壳头上。别再那样做。）

- **只认同一个小时**：`官方小时合计 − 我们 keep=1 合计`；差额 ≤ 0 或该小时没有唯一中断 → 留空
- 分配方式写进 `est_note`：多笔且都有正文长度 → **按正文长度加权**；否则 **均分**；唯一一笔写"唯一中断"
- 金额与 token **同进同出**（都来自同一小时的差额）
- 对不上的部分不塞给任何人：`gap_summary()` 报出 `官方 − 我们 − 已分摊 = 残差`

**对账表各列的精度（别搞混）**：
- **账本列只能到"分"** —— 官方余额接口返回的是 `"6.69"` 这种两位小数字符串，插件把它换算成
  `debitUnits`（1 亿分之一元）也只是把分表示出来，所以第三位**永远是 0，不是我们舍的**，是源头没有更细的信息。
  表头因此写「账本(元·分)」。
- **官方(小时桶) / events / ledger / 折算** 都是全精度计算值 → 显示 3 位。
- 最后一列是「**官方/折算**」（不是以前的账本/折算）：有官方数据时用官方列算，否则退回账本。
  这样才反映"我们 vs 官方"的真实偏差；账本÷折算会被"分"精度和同账户别的 key 的花费污染。

**逐小时对账日志**：每次 `--recon` 会写 `temp\official_recon.log`（UTF-8 BOM）：
`日期 小时 | 官方 | 我们 | 差额 | 中断 | 已分摊 | 补后残差 | 分配方式`，外加按天小计与"对不上"合计。

2026-09-28 实测（09-17~28 共 12 天，官方合计 71.677 元）：
**11 条空壳里 6 次是唯一中断（另 5 条是 fork 副本）**，6 次全部按小时对上、共恢复
**1.394 元 / 3,550,165 token**；其余小时差合计 1.220 元"对不上任何中断"，被单独报出。
其中 09-24 官方 18.663 / 我们 16.841，恢复 1.391 后还差 0.432。

### 2.6b 空转 / 重试：连壳都没有的调用（2026-10-20 加）

有的调用**钱花了、日志里连一行 `assistant/message` 都没有**：请求发出去后进程被 dispose、
服务端没回、或者重试了但没成。这类连「中断空壳」都算不上（空壳至少留了一条没有 usage 的 message），
所以以前只能在对账里露成差额。

现在按**次数**兜住：`db.sync_lost_calls()` 逐小时比较

```
official_hour.requests  vs  我们数得出来的调用数
                          = 正常 message + 中断空壳 + 原生搜索 calls_n + 压缩摘要
```

次数差 > 0 就把差额写进 `lost_calls`（`n` 次 + `cost` = 官方这一小时的钱 − 我们已折算的钱，
在 `sync_gap_estimates` **之后**跑，空壳先分走它那份）。**没 token、没正文、没会话**，
界面上是单独一行 `(未记录 · 空转)`（挂在 `(未记录)` 工作区下，次数按 n 摊成 n 行）。
对账的 `scan_cost`/`scan_calls` 和 `gap_summary` 的「我们」都算上它，所以能 100% 对上。

**只认次数差**：次数对得上、只是钱差一点的小时**不动** —— 那是价格/峰谷的问题，继续留在对账里
报出来。实测一次补齐：59 小时 / 115 次 / ¥1.3833（其中 10-17 那次空转 = 2 次 / 0.3120 元）。
**真删掉会话的不补**（日志没了，连次数都无从判断）。

### 2.6c 步维度 + 每次调用的摘要（2026-10-30 加，库结构 v6）

`messages` 里**每条 `assistant/message` 就是一次 API 调用**（带 `turn_no` / `step_no`），以前树最细只到
「轮次」，现在把「步」也做成一档维度（`hier.DIMS` 加 `step`，键 = `轮次.步`）。

- **摘要 `snippet`**：扫日志时取这条消息 content 里第一个非空块，优先 `reasoning`（思考链，正式输出通常在最后），
  压成一行、截 100 字；只给界面认"这一步在干嘛"，**不参与任何金额/token 计算**。
  实测 68% 的调用有思考链可摘，其余退回正文，再没有就空着。
- 界面：显示成 `第3轮·第2步 用户在问xxx…`（摘要截 36 字）；排序键补零，否则 `10.2` 会排到 `2.1` 前面。
- 代价：dashboard.html 从 ~4.7MB 涨到 ~6.0MB（1.3 万条 × 100 字）。老库靠 `MSG_COLUMNS` 补列 +
  `SCHEMA_VERSION=6` 触发一次全量重扫（14 秒）。

### 2.6d 工具调用（2026-10-30 加，库结构 v7）

`tool/call` / `tool/result` 也收进库：表 `tool_calls(session_id, day, turn_no, step_no, ts, call_id, name, ok)`，
`ok` 取 tool 消息的 `isError`。**工具本身不花钱，绝不参与金额/次数统计**，只做两件事：
解释"为什么这一步/下一步贵"（工具返回的大文本会进下一次调用的输入）、以及看这一步在干什么。

实测（455 会话）：**18,157 次调用 / 68 种工具 / 516 次失败**；`edit 5435 · pwsh 4956 · read 2108 · write 980`。

- **一次（轮,步）可以发起多个工具**：中位数 1 次，但 2~10 次的很多，长尾能到几十上百（多会话合并后的极端值）。
- **调用一定跟在某次 `assistant/message` 之后**（18,125 条 100% 如此）：模型调用 → N 次工具 → 下一次模型调用。
- 界面：表里多一列 **工具**（只有次数），鼠标悬停才显示 `edit×3 · pwsh×2`（叶子行）；父节点只显示合计。
- 老库靠 `SCHEMA_VERSION=7` 触发一次全量重扫（16 秒）把历史补齐。

### 2.7 高峰倍率自校准 + 节假日表（2026-09-28 加）

**要解决的问题**：`is_peak()` 原来只会"周末 + 两个窗口"，遇到**法定节假日**就把高峰算错了
（实测 09-25 中秋：官方 14/15/16 点按非高峰收，我们按 ×2 算，多出 0.986 元）。

**最终采用的做法：以官方实测为准（校验式），不用节假日表算钱。**

1. **判定**（`db.official_peak_decide()`）：抓好官方小时桶后，逐小时算
   ```
   倍率 = 官方金额 ÷ 官方 token 按【纯刊例价】的折算
   ```
   ≈2 → 高峰(1)，≈1 → 非高峰(0)，都不像（±8%）或金额 < 0.005 元 → **不判(None)**。
   **关键**：用**官方自己的 token**折价，所以"官方比我们多算的那几笔（旁路/缺账）"不会污染比值。
2. **落库**（`db.apply_official_peak()`，每次扫描末尾跑，幂等）：官方有定论的小时，把
   `messages.peak / cost_est` 改成实测倍率；**没官方数据或判不出来的小时一律保持原样**。
   结果整体重写进 `official_peak` 表（`peak_actual / ratio / base_cost / rule_peak`），
   供对账日志与看板引用。位置在 `scan_sessions.scan()` 里 **`rebuild_session_aggs` 之前**
   （先改原子行、再汇总，否则 sessions 的 `peak_cost/offpeak_cost` 会跟 messages 对不上）。
3. **节假日表（`config/holidays.txt` + `src/holidays.py`）只作对照**，**绝不参与实际开销计算**：
   - `off`（法定放假）= 全天非高峰；`work`（调休上班）= **也按非高峰**（DS 不认调休，
     照普通周末算；留着这些行只为对照与备查）
   - 文件里带一行【有效期】；**超出有效期**时该表不再参与判定（回落"只看周末"）并由
     `update_hint()` 给出"节假日表需要更新"的提示 —— 坏行/缺文件也只 warning，绝不崩
   - 对照工具 `src/holiday_check.py`：逐小时列「官方实测倍率 / 规则判定 / 节假日表判定 /
     **库内实际算钱的标记**」，末尾汇总三者各对多少小时
4. **维护节奏**：年底国务院发下一年通知后，把新一年行追加进 `config/holidays.txt`、改【有效期】那行。
   **能验证"调休不算高峰"的那天是 10-10（周六调休上班）** —— 那天跑一次 `holiday_check`
   就知道实测口径对不对（截至 2026-09-28 的数据里，09-20 调休日的 7 小时全在高峰窗口之外，
   所以这条规则**还没有实测证据**）。

2026-09-28 实测：86 个官方小时**全部**能定倍率，共改 **3 小时 / 125 行**（就是 09-25 那三小时）；
09-25 的对账残差从 **+0.986 元降到 +0.015 元**（剩下的 0.015 来自 0 点那一小时，与高峰无关）。
`holiday_check` 汇总：节假日表 对 86/错 0；规则判定 对 83/错 3；**库内标记 对 86/错 0**。

### 2.8 价目表 prices.txt（2026-09-28 加，库结构 v5）

**为什么不能只看模型名**：会话日志里 `data.model` 永远只有 `deepseek-flash` 这种**别名**
（DSH 自己的账本也一样），但它背后的模型和价格会变 —— `deepseek-v4-pro` 就被并进 flash
计价过。所以"这一笔按什么价"取决于 **(模型, 时刻)**，表就是干这个的。

表在 `config/prices.txt`（工具目录下）（**给人改的**，格式见文件头注释），解析在 `src/prices.py`：

```
号 | 模型 | 生效起 | 生效止 | 峰谷 | 谷价:命中,未命中,输出 | 峰价:... | 备注
1  | deepseek-flash  |                 | 2026-09-14 12:00 | yes | 0.02,1,4 | 0.04,2,8 | ...
```

- **生效区间**一律按**北京时间**比，起含止不含（`ts >= 起 and ts < 止`）—— 与 DSH 的计价切换点一致
- **同一个号可以给多行复用**（= 同一档价）；`messages.price_row` 记的就是这个号
- **匹配不到 / 多档重叠** → 未知价目：`price_row=-1`、`cost_est=-1`；重叠宁可判未知，也**不瞎猜**
- 文件缺了 → **内置兜底档**（= 1 号 flash 价）+ warning，保证看板不会空；刷新日志里会打出来
- 文件里有 `【本表核对到】YYYY-MM-DD`；DS 改价不会通知，隔段时间去核一次并改这一行

**踩坑提醒（改这块之前先看）**：
- 新增/修改任何**金额**查询，**必须带 `AND cost_est >= 0`**（自测里 `unk.*` 一组守门）
- 峰谷判定是**两个候选取更近**（§2.7），所以"峰价不是谷价两倍"也能判 —— **别再写死 ×2**
- `messages.price_row` 是 v5 新加的列；schema 版本一变 `scan` 会自动全量重扫一次
- 界面上：KPI 报"未知价目 N 次"、行内金额后面点一个蓝问号 `?`（`.unk-mark`），
  **钱不计但 token 照常统计** —— 别把未知价目当成 0 元混过去

### 2.9 原生搜索账单（旁路，2026-10-19 加）

**为什么要它**：`deepseek-official`（原生搜索）每次搜索都是一次**完整的 Anthropic Messages 调用**，
token 消耗不小（≈9k 输入 / 1k 输出/次），但**不写会话日志**。而官方小时桶**是含它的** ——
2026-10-19 14h 实测：官方 27 次请求 / ¥0.7150，会话日志只有 8 次 / ¥0.2565，差 **19 次**
= 12+6+1 次搜索，金额差 ¥0.4586 ≈ 搜索账单 ¥0.4334。不补这块，对账永远差一截。

**数据**：`~/.dsh/search-usage.jsonl`（`DSH_SEARCH_AUDIT_LOG` 可覆盖），由插件 `dsh-search-audit`
写，**只追加、一行一次搜索**，末行可能正在写（读的时候坏行直接跳过）。字段见 `doc/参考.md`。

| 字段 | 说明 |
|---|---|
| `ts` | 响应时刻（ms）；**没有 turn**，靠 ts 落进哪一轮来归位 |
| `sessionId` | **可能整个字段都不存在**（实测有一条）→ 按"时间邻近"推定（见下）；实在猜不出才归到"(未归属搜索)" |
| `usage.*` | `inputTokens`（未命中）/`cacheReadTokens`（命中）/`outputTokens`；**没有**写缓存 |
| `source` | `dsh-search-audit` = 实测；`estimate` = **N 次调用的聚合**（`query` 里写着"N 次"，`note` 写依据） |

**落库**：表 `search_calls`，**一行 = 一条 JSONL 行**（`calls_n` 记它代表几次调用），
`db.sync_search_usage()` 每次扫描重读整份（幂等，按 ts 覆盖），并顺手算好价目 + 规则峰谷。

**归到轮次**（`_turn_of`）：取「该会话里**轮起点 ≤ ts 的最后一轮**」；轮起点 = 该轮最早的
`start_ts`（用户提问时刻）。

**没写 `sessionId` 怎么办（2026-10-19 定规矩）**：**不自动猜**（猜错了钱会落进别人的轮次）。
账单每条理论上都该有 `sessionId`；第一轮测试时插件还没写，留了一条没有的 →
在 `config/search-fix.txt` 里人工补：`<ts> | <session_id> | 备注`，补出来的行 `note` 里会带
「（会话是人工补的：…）」可追溯。**以后再有查不出来的，就是插件/账单出问题了**：
扫描时打 `⚠ N 条没有会话归属` 警告，看板上也会明摆着出现 `(未归属搜索)` 节点。

**计价**：模型 `deepseek-v4-flash` 在 `config/prices.txt` 里登记（**号 3**，同 flash 价）；
峰谷先按规则判，`apply_official_peak()` 再按官方小时桶实测**把搜索行也一起校正**（同一小时同一倍率）。

**关于"每次搜索 ¥0.005"（2026-10-19 量化过，结论：不存在）**：

| 小时 | 官方 | 我们 | 残差 | 搜索次数 |
|---|---|---|---|---|
| 14 | 0.7150 | 0.6899 | **+0.0251** | 18 |
| 19 | 1.7969 | 1.7969 | **+0.0000** | 1 |

19 点那小时只有 **1 次**搜索，若有 ¥0.005 固定费，残差该是 **+0.005**，实测是 0.0000。
14 点 18 次搜索要真有固定费得 +0.09，实际只 +0.0251（扣掉反而更差 -0.065）。
所以按 **0** 计。当天总残差 +0.403 的主因不是它，而是 **21 点那小时的"压缩摘要"**
（`compaction/summary`，3 次 / 1.5M token，不走会话日志，落在 `side_calls` 的"未归因"里）。

**「搜索开销」列（2026-10-19 加）**：起止时间右边的诊断列，显示**这一行（含下级）里原生搜索
花了多少钱**（只算 token，固定费按 0）。悬停写明白：N 次、token 开销多少、为什么固定费是 0。
和「重建参考」共用同一个开关（`rbcol-off`），关掉一起收起来。

**默认不区分来源（用户口径）**：`build_data()` 把搜索行摊成**额外的原子行**塞进 `msgs`
（`estimate` 行按 `calls_n` 摊成 N 行，token 按 N 分、钱按每份 token 重算），
带 `kind="search"` —— 于是树/筛选/KPI/日聚合/CSV **全部自然包含**它，**不需要新增维度**。
界面上只在 KPI 多一行「其中原生搜索 N 次 · X 元」，提醒它已经并进合计、不单列。

**对账侧**：`gap_summary()` 的 `ours` 按小时把搜索并进去；`rebuild_day_recon()` 的 `scan_cost`
也加上它（搜索同样是"我们的花费"）。这样 10-19 14h 残差从 +0.4586 降到 **+0.0251**、
19h 变成 **0.0000**。

**已知边界**：
1. 只覆盖插件安装之后的搜索（本机 2026-10-19 19:36 起）；更早的只能人工补 `estimate` 行。
2. 只覆盖**原生引擎**（`deepseek-official`）。free-search 各引擎的调用是普通工具结果，
   token 早已在会话日志里，**再记一遍就是重复计费**。
3. `hier.py`（终端版）**不含**搜索账单（它只查 messages）；CSV 导出走 `build_data()`，是含的。
4. KPI 的「其中原生搜索」是**按当前筛选结果**算的（跟着时间窗/工作区变），不是全局数。

### 2.10 疑似缓存重建（「重建参考」列，2026-10-19 加）

**现象**：正常的一轮，第一条调用几乎全命中缓存（前缀在服务端缓存里）；但偶尔会有一轮
**首调用整段上下文全未命中**，紧接着第二条又回到 0% —— 那是服务端缓存没了、整段重算了一遍，
钱按未命中价全付。实测最贵的一次：633,865 token 全未命中，多花 ≈1.24 元。

**判据**（`db.turn_rebuild_flags()`，三个常量都在函数上方）：

| 线 | 条件 | 说明 |
|---|---|---|
| 硬线一 | 该轮**第一条调用**未命中率 ≥ `RB_LOOSE_MISS`(50%) / ≥ `RB_STRICT_MISS`(70%) | 宽判 / 严判 |
| 硬线二 | 该调用上下文 ≥ `RB_MIN_CTX`(50k) | 太小的重建也就几分钱，不看 |
| 确认线 | 严判额外要求：同轮**第二条**未命中率 < `RB_CONFIRM_MISS`(10%) | 区分"真重建"（爆一次回落）和"这轮本来就塞了很多新内容" |

**代价**：`miss × (未命中价 − 命中价)`（按该行的价目档与峰谷），即"如果缓存还在会省多少"。

**界面**：columns 最后一列「重建参考」（在「起止时间」右边、具体 token 数三列左边）。

- **三档，只给这一格的字上色、不动整行**：严判通过 → **红字**（`.rbcell.strict`，用 `--hot-fg` 那支红）／
  只过了宽判 → **黄字**（`.rbcell.loose`，`--rb-fg`）／都没过 → **灰横杠**（`.rbcell.none`）
- 行内数字是**本行（含下级）累计**；`合计` 那行是当前筛选下的总和
- ⚠️ 这是**纯展示**：钱本来就含在 `cost_est` 里，这一列只是把它拆出来看 ——
  **不进 KPI、不进聚合、不进筛选、不进 treeKey**（自测 `rb.not_in_daily_cost` 守这条）

**实测（2026-10-19 全库）**：1279 轮里 **38 次**疑似重建（全是严判），估算多花 **¥10.38**，
占全部花费 ¥159.56 的 **6.5%** —— 不算小数目。

**开关**：操作区「重建参考列」勾选框（`S.showRb`，默认开、进 `PERSIST_KEYS`），
关掉=给表格加 `rbcol-off` 类整列隐藏（和「具体 token 数」一个套路，切类在 `render()` 里）。

悬停有 tooltip 说明是宽判还是严判、以及多花了多少。

**表格宽度（2026-10-19 顺手压的）**：内边距 3×7→2×5；占比条最小宽 104/64→72/40；
层级/会话名与起止时间改成 `.lblwrap` 单行省略号（`max-width:min(460px,32vw)` / `min(170px,14vw)`，
窄屏自动缩短，悬停看全文）—— 目的是**别出横向滚动条**。

### 2.10b 次数维对账：`req_check.py`（2026-10-20 加）

钱差一点的时候，光看金额分不清"价格算错"还是"根本没记到"。**次数**最直白：官方小时桶有
`requests`，我们这边数得出来 ——

```
我们调用数 = 正常 message + 中断空壳 + 原生搜索 calls_n + 压缩摘要
```

`python src\req_check.py` 打逐小时对比，差 ≥3 次的排前面。实测（09-17 ~ 10-20）：
官方 13041 次 / 我们 12922 次，**差 119 次（0.9%）**；171 小时里 65 个有差异，但差 ≥3 的只有 7 个，
最大的是 09-18 21h（+22 次）。**大部分小时严丝合缝**。

差出来的那些是"请求发出去、钱花了，但日志里没有 assistant/message"：重试、中止、
turn 被硬删（本机装了 `dsh-turn-hard-delete`）、或者对面根本没收到。**这类补不了**
（没有 token 账可算），只能手工补金额 —— 做法见下面 §2.11 末尾的"手工补记"。

### 2.11 压缩摘要（compaction/summary，2026-10-19 加）

**它是什么**：上下文快满 → DSH 压缩时那次"写摘要"的模型调用。**也是一次完整的模型调用**
（还会把整段上下文按未命中价重发一遍，所以一次就是 0.5 元级），但它**不写成
`assistant/message`**，所以以前既不在轮次里、也没算钱 —— 对账时就在官方那边露成一个"差额"。

**落库**：表 `compaction_events`（`ts` 主键 = 天然去重）。采集在 `side_calls.py`（它本来就在
逐行读会话日志），`db.sync_compactions()` 负责：按 ts 去重（**分叉会话里同一份摘要各记一次**，
认创建更早的会话，跟消息去重同规矩）→ 定价（模型取事件自带的，没有就取该会话最近一次调用的）→
`apply_official_peak()` 也把它的峰谷一起校正。**每次整表重算**（事件很少，且 side_calls 可能
先于主扫描跑，重算能让"先跑谁"不影响结果）。

**挂到轮次**：按 ts 找它落进的那一轮，再跟该轮首/尾消息比时间，得出 `pos`：
`前` / `中` / `后`。`build_data()` 摊成额外原子行，**轮次键用 `turn + 0.5`**（所以排在那轮后面），
标签走 `labels.turn` 注入：**「第 N 轮中 · 压缩摘要」**（没有轮次时显示「会话开始前 · 压缩摘要」）。
默认排序按"结束时间"，所以 12.5 这种小数键天然落在两轮之间，**不用改排序**。

**对账**：`gap_summary()` 的 `ours` 与 `rebuild_day_recon()` 的 `scan_cost` 都并入它。
实测 10-19 21 点：残差 **+0.5074 → +0.0000**，全天 **+0.403 → −0.116**（剩下的是当天还没结算的小时）。

⚠️ 它同时从 `side_calls` 的汇总里**拿掉了**（以前 `compaction/summary` 被当普通旁路调用按天汇总，
3 次其实全是同一份的副本），避免两处各算一次。2026-10-20 又补一刀：`side_calls.scan` 每次先把
`side_session` 里的 `compaction/summary` 行**删掉**（历史遗留的按天汇总），否则对账表的
「旁路token」列会一直显示几百万 —— 那些其实全是压缩摘要，已经单独入账了。
现在「旁路token」列正常是 `-`（真的没有别的旁路调用时）。

**历史摘要要"全量"才补得齐**：`side_calls` 只重解压变动过的会话，所以在加这个功能**之前**发生的
摘要（09-24 / 10-02 / 10-03 / 10-05 / 10-06 …）要等一次 `--full` 才会被收进来。
补齐后实测 11 次 / ¥1.665 / 5.44M token（大部分是缓存命中，所以钱不多）。

**手工补记（没有日志的钱）**：遇到"官方有、我们完全没记录"的，直接往库里插一条
**0 token、只有金额**的调用（挂在一个 `(手工补记)` 工作区的合成会话上），走正常口径
（折算 / 对账 / 树 / 日聚合都自动算）。2026-10-17 20:36 那次空转就是这么补的：
差 0.3120 元 → 补完那天 100.0%。**不要**为此加新机制，就是一次性数据修补。

### 2.12 性能：增量与缓存（2026-10-19 大修）

**目标**：日常刷新只做增量、几秒出图。**实测 41 秒 → 4.5~7 秒**（要在网上抓官方数据时再加 8 秒左右）。

| # | 改动 | 前 → 后 | 说明 |
|---|---|---|---|
| 1 | `db.rebuild_session_aggs()` 重写 | **34 秒 → 0.05 秒** | 原来是**一个 UPDATE 带 11 个相关子查询**（每个会话再扫一遍 messages，438×11×全表 ≈ 几千万行）。改成先 `GROUP BY session_id` 一趟算完、再逐会话 UPDATE。**教训：相关子查询别放进覆盖全表的 UPDATE** |
| 2 | `scan()` 删掉无用遍历 | 436 次查询 → 0 | 未变动的会话本来就不参与"谁最早"的判定（`owner` 已经一次查好），以前却逐会话把消息捞出来再全局排序 |
| 3 | `side_calls` 改增量 | **14.5 秒 → 0.8 秒** | 以前每次把所有会话日志解压一遍（438 份 / 60MB）。新增 `side_session`（逐会话明细）+ `side_log`（水位），`side_calls` 变成它的 `GROUP BY` 汇总 |
| 4 | 显示名按需读 | 0.78 秒 → 0 | `sync_labels` 要读 440 个 JSON；没有会话变动就不读（`labels` 表为空时例外） |
| 5 | `refresh.py` 只扫一次 | 少一整遍扫描 | 原来"扫一遍 → 抓官方 → 再扫一遍"，现在"抓官方 → 扫一遍（含对账）" |
| 6 | `ds_usage --max-age-min`（默认 3 分钟） | 5 秒 → 0 | 刚抓过的天不重复抓，连点两次刷新不再等网络；`--force` 无视冷却 |
| 7 | 看板的 node 自检按模板指纹跳过 | 2 秒 → 0 | `app.html`/`app.js` 的哈希存进 `meta.js_check_sig`；**模板改过就还会跑**（安全网没丢） |

**口径一个字节都没动**：这些全是"算了但不影响结果"的东西。两条自测守着：
`agg.per_session_matches_messages`（sessions 聚合 == messages 现算）、
`side.*`（旁路增量幂等 + 汇总 == 逐会话明细）。

**全量刷新入口（2026-10-20 补回）**：`python src\refresh.py --full`，或双击 **`全量刷新.bat`**。
全量 = 所有会话日志重扫 + **官方小时桶强制重抓**（`ds_usage --force`；平台偶尔只返回部分小时，
不重抓就会一直少算 —— 实测 10-06 只有 8 个小时、10-05/10-07 各 2 个小时，那天就会显示"我们比官方多很多"）。
日常还是用 `刷新看板.bat`（增量，几秒）。

**对账表的比率列改成「折算/官方」（2026-10-20）**：以前是"官方/折算"（比值 >1 表示官方更多，反直觉），
现在是**百分比**：`100.0%` = 我们统计到的和官方一样多，`90%` = 只统计到九成，`110%` = 多算了一成。
没有官方数据的天显示 `-`。

⚠️ **备注也跟这一列同一个口径（2026-10-20 修）**：以前备注算的是"账本 ÷ 折算"（`factor`），
跟表里显示的"折算/官方"根本不是一回事 —— 于是会出现「比率 100% 却写着偏差>15%」这种怪事。
现在备注只用 `折算/官方`：差超过 15 个百分点才提示，并直接写出百分比和差多少；
没有官方数据写「无官方数据」，当天写「当日数据未结算」，没有会话记录写「无会话记录」。
**还能再省（没做，收益 <1 秒）**：显示名逐会话增量（现在只要有会话变动就全读 0.8 秒）。

### 2.12b 树表分页渲染（2026-10-30 加，解决"层级到底层就卡死"）

问题：选了 `会话 › 轮次 › 步` 这种三层到底，可视行数能到 **1.6 万行**，一次 `innerHTML` 全画出来
就是 25 万个 DOM 节点，浏览器直接卡死（还会触发逐行 `onclick` 绑定，更慢）。

做法（等价于"虚拟滚动"里最省的那种：**增量渲染 + 滚动加载**）：

- `paintRows(keep)` 一次最多画 **400 行**（`PAGE`），行数多于这个就在表尾放一行
  `已显示 400 / 16084 行 · 继续向下滚动加载`；
- `window` 的 scroll 里用 `requestAnimationFrame` 节流，判断表尾那行的 `getBoundingClientRect().top`
  是否进入视口下方 400px，是就再画 400 行（上限 4000，避免一次把整张表又铺回来）；
- **事件委托**：不再给每行挂 `onclick`，只在 `#treeRows` 上挂一个，靠 `e.target.closest("tr[data-path]")` 找行；
- 选节点/改层级时保留已展开的行数（`S.shown`），不会一选中就缩回 400 行；
  折叠/展开时重置为 400。

效果：首屏 DOM 从 25 万节点降到 ~6 千（16 列 × 400 行），滚到底再追加。
`tests: pager.footer_rendered / pager.rows_capped` 两个断言守住"一次不超过 400 行"。

**还没做的**：treemap / 旭日图同样会一次画全部叶子（底部维度很多时不比树表轻），
要优化可以按"前 N 大 + 其他"聚合，目前没那么用就先放着。

**对外发布相关的三条（2026-10-30 加）**：
- **key 名自动识别**：`db.resolve_key_name(con)` —— 环境变量 `DSH_API_KEY_NAME` → 库里花钱最多的
  `api_key_name` → 兜底 `"harness"`。以前写死 harness，别人拿到会静默「官方对账全空」；
- **`看板窗口.bat`**：用 Edge/Chrome 的 `--app=file:///...` 打开看板，得到独立窗口（不打包 exe、
  不加依赖），找不到浏览器就退回默认打开方式；
- **`.gitignore` + `config/usertoken.txt.example` + `README-FOR-AI.md`**（给接手方 AI 看的说明）。

## 3. 界面（app.js）关键机制

### 3.1 三个排序下拉 = 三层各管自己

```
sortOf = [第1层模式, 第2层模式, 第3层模式]
每层可选：ts(时间↑) / ts_desc(时间↓) / cost / tokens / calls（后三个都是降序）
```

**实现要点（踩过坑，改动时注意）**：
- 排序的是 `nd.children`，用的必须是**子节点的层号** `nd.depth + 1`，
  不是父节点的 `nd.depth`。用错会"串位"：第 1 个下拉排了第 2 层、第 3 个永远轮不到。
- 并列时按**显示名**排（不是原始 id），否则界面上会出现"名字看着乱序"。
- 第 1 层的父是**根节点**，不在 `sortByDepth`（该结构只收录非根的多子节点）里，
  自动化验证第 1 层要看快照的 `top`。

### 3.2 折叠与选中用「路径」而不是数字 id

节点路径 = 各级值用 `\u0001` 连接（首段不带分隔符）。**为什么不用数字 id**：
数字 id 是排序后按遍历顺序分配的，一换排序整个重排、id 全变，
折叠状态就"继承不下去"（这是修过的 bug）。

DOM 上用 `data-path` 标识行；`S.collapsed` / `S.selected` 存路径。
路径与排序无关，所以换排序/换层级后依然指向同一内容。

### 3.3 列的语义（app.html 表头 + app.js 渲染）

```
层级 | 花费 | 占父级 | 总占比 | 总token | token占比 | 开销占比 | 峰值 | 调用 | 起止时间 ‖ 具体token数(默认隐藏)
```
- **token 占比**：三种 token 按**数量**分
- **开销占比**：三种 token 按**各自贡献的钱**分（两者对照 = "量大 ≠ 贵"）
- 占比条：用 `display:table` 的单元格，百分比写在色块里，太窄的段自动不显示数字
- 具体 token 数三列默认隐藏，由「显示具体 token 数」开关切换（`table.rawcol-off` 类）
- **三列在"整棵子树没有一点 usage"时显示 `—`（不是 0）**：0 的意思是"这次调用真的只花了 0 token"，
  而中断空壳是"压根没记到 token"，两者不能混（`app.js` 的 `rawCols()`）
- ⚠️ **`rawcol-off` 这个类必须在 `render()` 里切**（视图切换那段）：`render()` 是所有改状态
  的入口（复选框、预设、URL hash 都走它），只在 `refreshControls()` 里切会出现
  **"点了复选框没反应"**——2026-09-28 踩过（显示具体 token 数打不开）。加新的显示开关照这个模式。
- 排查这类"开关点了没反应"：`python src\render_html.py` 的假 DOM 会真跑一遍；
  自测里 `raw.*` 一组就是拿 `document.querySelector("table.t").classList.contains(...)`
  直接验"类切没切"。另外**默认层级只到「会话」**，想看单个空壳/单次调用要先把层级下到「轮次」/「模型」。

### 3.4 标红阈值（`S.hotCost` / `S.hotPeak`，2026-09-25 加）

操作区那一栏「标红：花费 > __ 元 / 峰值 > __ %」**只上色、不过滤**：
- 花费超阈值 → `td.hotcost`；峰值超阈值 → `td.hotpeak`；命中任一项整行加 `tr.hot` 底色
- 阈值填 `0`（或空 / 负数）= 关闭该项；`oninput` 触发一次 `render()`
- **「只标红最下层」勾选（`S.hotLeafOnly`）**：只标"当前屏幕上最深的那一层"——
  判据就一句 `node.children.length === 0 || collapsed`（没有下级、或下级被折叠）。
  所以折叠一个父节点，它自己立刻变成最下层、可以被标红；展开着的父层不标。
  这条跟折叠状态联动，但**不改折叠、不改过滤**，只是每行多算一个布尔
- **判定只在 `render()` 里产出 class**，绝不进 `currentRows()`、聚合、KPI、`filterInfo`
- 自测里有 `hot.*` 一组守门用例：把 `hot/hotcost/hotpeak` 这些 class 抹掉后，
  行 HTML 必须与原样**逐字相同**，且 KPI 不变 → "标红不碰数字"
- 峰值比对用**未取整**的百分比（列里显示的是 `toFixed(0)`），所以显示 50% 而实际 50.4% 时仍会标红

### 3.5 树图 / 旭日图

- treemap：只画叶子（面积=当前指标），父级用**标题带 + 留边**表示层级；
  切分必须保证切点在 `[1, n-1]`，否则退化成"两组都是全集"**无限递归**（踩过，浏览器会静默吞掉）
- 旭日图：由内向外三层同心环
- 两者的点击下钻都用 `data-path` → `selectNodePath()`

### 3.6 预设查看模式 + 记住上次状态（2026-09-25 加，纯前端）

操作区**第二行**那个「预设」下拉。**它不是状态显示，是一组按钮**：选完执行一次、立刻弹回
占位符（`选择预设…`），所以不存在"手改了别的它却还显示预设二"的假信息。

**清单不在代码里，在 `config/presets.txt`（工具目录下）**（每行一档、用 `|` 分隔、`#` 注释），
生成看板时由 `render_html.load_presets()` 读进来、塞进 `DATA.presets`：

```
名字 | 层级 | 日期 | 排序 | 花费标红(元) | 峰值标红(%) | 只标最下层(yes/no)
今天 · 工作区›会话›轮次 | workspace,session,turn | today | ts_desc,ts_desc,ts_desc | 0.5 | 0 | yes
```

- 某一格留空 = 那项不动；**坏行只跳过并记一条 warning**（显示在预设旁边的小字里），
  缺文件就退回 `app.js` 的 `BUILTIN_PRESETS`，**永远不影响看板生成**；
- `日期` 只认 `today`（= `latestDay()`）/ `full`（= `DATA.range[0]` ~ 最新一天）/ 空；
  这两个档位在 `app.js` 的 `RANGES` 里，加新档位就往那儿加一行；
- `排序` 只写一个值 = **三层都用它**，也可以分开写三个；
- **id 0「上次状态（刚打开时）」是代码加的**（`SNAPSHOT_PRESET`，= `P0_SNAPSHOT`），
  配置文件里没有它、也不该有。

两条必须记住的规则（改代码时别踩）：
- **`range:"today"` 用 `latestDay()`（库里最后一天），不是系统日期**。用系统日期的话，
  今天还没刷新库时整个页面会是空的。
- **`dims` 一变就必须清 `collapsed` / `selected`**：它们按路径存，换了维度路径就全变了。

状态记忆（"继承上次"）：
- `PERSIST_KEYS` 里的键在每次 `render()` 末尾由 `saveState()` 写进 `localStorage`
  （键名 `dshTokenStats.view`）；打不开 `localStorage`（`file://` 被禁等）就**降级写地址栏
  `#state=…`**（用 `history.replaceState`，不刷历史记录）；两条都不通就只是"不记住"，
  功能照常，下拉旁边会写一句"本浏览器不让记住"。
- 启动顺序（`init()`）：`applyState(loadState())` → `parseHash()`（URL 显式参数优先）→
  `fillPresets()` → `refreshControls()` → `P0_SNAPSHOT = snapshot()` → `render()`。
  **`refreshControls()` 不能省**：它负责把状态推回输入框/勾选框，否则"值变了但控件还显示旧数字"。
- **不持久化**：日期（每次默认 `DATA.range[0]` ~ 最新一天）、关键字、折叠、选中行。
  存的快照里也没有它们，所以预设 0 同样不碰日期。
- 恢复时逐项校验（`applyState`）：维度不认识、数字是 `"abc"`、`view` 是新词、`workspaces`
  不是数组……一律丢掉或钳到合法值，**绝不让脏数据把页面搞崩**。
- 万一被记住的状态让你看着"数字不对"：勾一下空间区的「全选」、或点预设 0，都能救回来。

### 3.7 异常黄标 + 「含异常」开关（2026-09-28 加）

- 带中断空壳的行：**琥珀色**（`tr.anom`）+ 名字前一个 `⚠`（`.anom-mark`）+ 悬停说明
  （几条中断、估算多少钱、当前计没计入）。**刻意不用红色**——红色那套被"超标标红"占着，

### 3.8 时间范围细分到分钟（2026-10 加）

操作区第一行：`日期 [date] 时间 [time] ~ 日期 [date] 时间 [time]` —— **时间/空间各占一行**，
时间后面各跟一个 `type="time"` 的分钟输入框。

- 状态是 `S.fromTime` / `S.toTime`（字符串 `"HH:MM"`），**默认 `00:00` / `23:59`**（= 整天）；
  和 `S.from` / `S.to` 一样**不持久化**（每次打开都回到默认）
- `rangeBounds()` 把「日期 + 分钟」换算成毫秒边界；**结束那一分钟整分钟都算进去**
  （填 `23:59` = 一直算到 `23:59:59.999`，等价 24:00，省得让人填 24:00）
- `currentRows()` 改成按 **`m.ts`** 比（以前是按 `m.day` 字符串比）
- `setRange(from, to, keepTimes)`：改日期传 `keepTimes=true`（**不冲掉**用户填的分钟）；
  点「全部 / 近 7 天 / 最新一天」、套用预设、URL hash 里的 `range=` 都会复位成 `00:00 / 23:59`
- 控制条上的 `$("fromTime")` / `$("toTime")` 的 `onchange` 必须走 `setRange(..., true)`（改完要重画）

**两个必踩的坑**：
1. ⚠️ **`treeKey()` 必须带上 `S.fromTime` / `S.toTime`** —— 否则改了分钟 `getTree()` 命中旧缓存，
   界面上一点反应都没有（和 `withAnomaly` 那次一模一样的坑；自测 `min.narrow_tree_refreshed` 守这条）。
2. ⚠️ **本地日期一律用 `ymd(d)`，不要用 `d.toISOString().slice(0,10)`** —— `toISOString()` 是 UTC，
   在 UTC+8 下会整体退一天（"近 7 天"曾经实际跨了 8 天，就是这个 bug）。

**已知的刻意取舍**：底部的「按天」柱状图和「对账表」仍然是**天粒度**（它们是按天预计算的数据），
时间窗只影响树/树图/旭日图/KPI。要做到分钟级一致得改 `build_data()` 的日聚合，暂时不做。

### 3.9 深色模式（2026-10 加）

操作区最后一行那个「深色模式」勾选框：勾上给 `<body>` 加 `dark` 类 → 黑底白字。

**做法是"换一套 CSS 变量"，不是重写样式**：

- `:root` 里集中定义中性色：`--bg / --card / --line / --fg / --dim / --fg2 / --input / --hover /
  --grid / --on / --on-line / --empty / --tile / --d1~--d3`；`body.dark{}` 里**只覆盖这些变量**。
  图例色 `--c1~--c5`、色块上的白字、错误红一律不动。
- **告警色在深色下换成"和黑底混出来的"版本**（也是变量）：浅色模式是"亮底 + 深红/深黄"
  （`--hot-bg:#fdecea` / `--hot-fg:#c62828`、`--anom-bg:#fff8e6` / `--anom-fg:#b26a00`）；
  深色模式换成"暗红/暗琥珀底 + 亮红/亮黄字"（`--hot-bg:#331d1c` / `--hot-fg:#ff8b80`、
  `--anom-bg:#332b19` / `--anom-fg:#f2b34d`）。**语义通道不变**（红=超标、黄=异常）。
  蓝问号 `--unk-fg`、琥珀提示 `--warn-bg/--warn-line`、脚本错误红也都走变量。
  自测 `dark.light_signals_kept` / `dark.hot_mixed_with_bg` / `dark.anom_mixed_with_bg` /
  `dark.signals_use_vars` 守这四条（浅色值保留、深色值确实是暗底混色、规则都走 `var()`）。
- ⚠️ **原生控件要单独管**：`<input type="date">` / `type="time"` 的**右侧小图标**、**弹出的日历/时钟面板**，
  `<select>` 的选项弹层、滚动条，都是浏览器自己画的，**普通 CSS 碰不到** —— 只认 `color-scheme`。
  所以有 `:root{color-scheme:light}` / `body.dark{color-scheme:dark}`，另加一条
  `input[type=date],input[type=time]{background:var(--input);color:var(--fg)}` 把框体钉死。
  （2026-10 踩过：深色模式下时间选框还是浅色，就是缺这个；自测 `dark.color_scheme_*` 守三条。）
- **图（SVG）也跟着变**：donut 轨道、坐标轴、坐标文字、treemap 底色改用
  `svg .track / .axis / .lbl / .val / .tilebg` 这几个 class（CSS 里用变量定义）。
  ⚠️ **SVG 的"表现属性"（`fill="#xxx"`）里不能用 `var()`** —— 变量只在 CSS 声明里生效，
  所以要么挂 class 让 CSS 管，要么写 `style="fill:var(--x)"`。色块上的白字仍写死 `#fff`。
- 状态 `S.dark`：进 `PERSIST_KEYS`（"记住上次状态"）＋ `applyState` 的布尔列表 ＋ `refreshControls`；
  **切 `body.dark` 的动作放在 `render()` 里**（和 `rawcol-off` 同一个道理：render 是所有改状态的入口）。
- ⚠️ 改测试脚手架时注意：`render_html.NODE_HARNESS` 的假 `document` **必须带 `body`**
  （`document.body.classList` 要用），2026-10 加深色模式时补上的。

## 5. 踩过的坑（照着躲）

### 5.0 `.bat` 别带 Low 完整性标签（否则双击弹“安全警告”）

2026-10-20 实测：`token统计` 整个目录被 `icacls /setintegritylevel Low /T` 递归打过标签后，
**双击 `刷新看板.bat` 会弹 Windows「打开文件 - 安全警告」**；而当天新建的 `全量刷新.bat`
（宿主工具创建的，默认没有标签 = Medium）双击就能直接跑。两个文件的内容/编码/BOM 完全一致。

- **原因**：Windows 把“低完整性”的脚本/可执行当不可信来源（跟“从网上下载”的 Zone.Identifier
  是两条路，表现都是那个警告）。跟 .bat 内容无关。
- **规矩**：**`.bat` 用 Medium（默认）**。新建的本来就是 Medium，别被 `/T Low` 打上；
  一旦被打上就改回来：
  ```powershell
  icacls 刷新看板.bat /setintegritylevel Medium
  ```
- **只有 .bat 需要这样**：`token统计` 里其它文件（数据库、看板 HTML、日志）必须保持 **Low**，
  否则沙箱里的 python（低完整性）写不进去 —— 2026-10-20 那次“数据库只读”就是这么来的。
  所以整个目录 Low 是对的，单独把 `*.bat` 设回 Medium 即可。
- 批量检查/修复：
  ```powershell
  Get-ChildItem *.bat | ForEach-Object { icacls $_.FullName /setintegritylevel Medium }
  ```


### 5.1 `.bat` 里不能出现非 ASCII 字符
cmd 按系统 ANSI(GBK) 读批处理文件，而脚本里 `chcp 65001` 之后 cmd 对**批处理正文**的解码会错位，
中文路径直接变乱码（`python 看板.py` → `python ???.py`）。
**所以**：批处理正文全 ASCII（提示文字用英文），中文提示交给 Python 打印；
入口脚本也改名为 ASCII（`refresh.py`），看板本体用 `dashboard.html`，
另留 `看板.html` 作为跳转页。

### 5.2 `db.connect(path=DB_PATH)` 的默认参数
默认参数在**函数定义时**求值，之后改 `db.DB_PATH` 不生效 → 测试会写到真实库。
正解：签名写 `path: str = None`，函数体内 `sqlite3.connect(path or DB_PATH)`。

### 5.3 测试脚手架的坑（`render_html.NODE_HARNESS`）
- 假 DOM 的 `__mk(id)` 必须对同一 id 返回**同一实例**，否则"模拟点下拉"这类交互断言全是假的
- 结果快照必须在**注入的交互代码之后**采集，否则读到的永远是初始状态
- 不能用 `process.stdout.write` 输出测试数据（会和 harness 自己的 JSON 撞车）；
  要带数据出来就塞进 `DATA.xxx`，让快照顺带带出
- `subprocess.run(text=True)` 在 Windows 上按 GBK 解 node 输出，必须显式 `encoding="utf-8"`

### 5.4 本机沙箱的两个限制
- headless Edge/Chrome 需要**命名管道**（mojo IPC），当前沙箱会拦 → 截图要一次性提权
- `db.py` 被 `import` 和 `python db.py` 两种方式加载时可能生成**两个模块对象**，
  测试里改路径要两边都改

### 5.5 其它
- `src/app.html` 是模板（没有数据），**别当入口点打开**
- 手工重渲染时记得 `--out dashboard.html`，默认输出已是 `dashboard.html`，
  但历史上曾误把 `看板.html` 覆盖成活看板
